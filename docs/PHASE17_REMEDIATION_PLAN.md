# Phase 17 후속 보완 계획 — 분류 대상과 불확실성 처리

> 2026-10-12 · 승인된 보완 구현·검증 종료. API 조합은 채택, E4B는 개발 단계 미선정. 실제 결과와 제한은 [후속 검증 기록](PHASE17_REMEDIATION_VALIDATION.md)에 분리한다.
> 기존 [승인 계획](PHASE17_PLAN.md)과 [실패를 포함한 검증 결과](PHASE17_VALIDATION.md)를 보존한다. 아래 계획·채택 기준은 유지하며 이전 후보를 소급해 채택 처리하지 않는다.
> SinglePass 기본값을 유지하며 2단계는 검증한 `gpt-5.6-luna` API 조합만 선택할 수 있다. E4B는 비활성 상태다.

## 목표와 범위

같은 모델을 두 번 호출하는 선택형 경로에서 정상 요청 누락, 잘못된 관계 신호와 다른 대상의 상태를 답하는 오류를 줄인다. Phase 12의 변수 계산·행동 선택을 유지하고, **모델에 전달하는 분류 과업의 범위와 대상, 분류 결과의 대응 관계, 대사 단계의 지침 우선순위**를 보완한다.

대상은 기존 Windows E4B/llama.cpp b11146 Vulkan과 Backend V4의 `gpt-5.6-luna`다. 모델·실행기·Unity `6000.5.3f1`·패키지 `0.4.0`·의존성을 유지한다. Android·LiteRT/E2B·LFM2.5 신규 지원, Phase 13·14, 학습·모델 교체, 세 번째 모델 호출, 자동 재시도·온라인 전환은 제외한다.

## 채택 실패의 직접 원인

기존 96개와 당시 신규 24개를 각각 두 번 평가한 **2단계 후보** 결과다. 응답 시간은 추론 요청 경계이며 전체 NPC 제출 시간은 아니다.

| 모델 | 기존 96 신호 / 기준 | 당시 신규 24 신호 / 기준 | 상태·기억 기존 / 신규 | 행동 신호 오탐 | 요청 p95 기존 / 신규 |
| --- | --- | --- | --- | ---: | --- |
| E4B | 190/192 / 183 이상 | **44/48 / 46 이상** | 38/38 · 22/24 | 0 | 2.339 · 2.315초 |
| API | **178/192 / 183 이상** | **45/48 / 46 이상** | 38/38 · 24/24 | 0 | 3.452 · 3.903초 |

두 모델 모두 신호 기준 미달로 탈락했다. 상태·기억 점수나 빠른 응답으로 신호 실패를 상쇄할 수 없다. 생성 오류·timeout은 없었으며, 모델별 반환 신호를 Basic/Advanced에 재생한 규칙 계산은 각각 480/480이었다. 이것은 **잘못 분류한 신호까지 규칙대로 처리했다는 뜻**이며 사용자 의도와 효과가 모두 일치했다는 뜻은 아니다.

### 증거로 확인한 사항

1. **API의 정상 요청 보류가 주된 실패다.** 2단계 신호 실패 17턴 중 15턴에서 문 열기가 `uncertain`이었다. 나머지 두 턴은 인사에 칭찬을 더하거나, 모욕 대신 칭찬을 반환했다. 처음 잘못된 값은 분류 배열에 있으며 ID 변환·규칙 계산은 해당 값을 정확히 따랐다.
2. **같은 입력도 결과가 달랐다.** API 분류 payload 전체를 정규화해 묶으면 240회는 85종 입력이며, 5종에서 서로 다른 배열이 나왔다. 현재 문장이 `문을 열어 주세요.`인 동일 payload 20회 중 11회는 `match`, 9회는 `uncertain`이었다. 게임 허가·호감도에 따른 입력 차이로 이 그룹의 차이를 설명할 수 없다. 반복 횟수를 독립적인 새 표현의 수로 계산하지 않는다.
3. **E4B는 참조와 절별 대상 해석에 약점이 남았다.** 이전 복수 대상 요청과 새 참조 실행 요청에서 문 열기를 누락했고, 다른 사람의 친절과 NPC의 불친절을 함께 말한 문장에서 모욕을 누락했다. 각 유형은 두 회차 모두 재현됐고 실제 배열은 모두 `no_match`였다.
4. **E4B의 상태 오류는 대사 생성에서 발생했다.** 과거 창문의 닫힘과 최신 출입문의 열림이 모두 입력에 있었는데 출입문을 닫혔다고 답했다. 최신 관찰 블록 누락, 토큰 계산 오류나 이력 잘림으로 확인된 사례가 아니다.
5. **대사 입력에 지침 충돌 가능성이 있다.** 동결 fixture의 작성된 `goalsAndValues`에는 매 턴 트리거를 분류하라는 문장이 있고, 대사 단계의 시스템 지침에는 다시 분류하지 말라는 문장이 있다. 두 문장의 공존은 확인했지만 이것이 특정 상태 오류의 원인인지는 분리 실험이 필요하다.
6. **이전 후보 선택은 E4B 개발 결과에 의존했다.** E4B에서 고른 조합을 API에 그대로 적용했다. API는 상태·기억이 개선됐지만 기존 집합 신호는 SinglePass 192/192에서 178/192로 내려갔다. 같은 프롬프트 보완이 두 모델에 같은 효과를 준다는 가정은 성립하지 않았다.
7. **평가 범위에도 빈틈이 있다.** E4B가 참조 요청을 그대로 따라 말한 응답은 상태·기억 질문 부분집합 밖이라 그 의미 지표에 포함되지 않았다. 신호 실패로는 이미 잡혔으므로 옛 점수를 바꿀 이유는 없지만, 다음 검사에는 요청에 답했는지도 별도로 포함해야 한다.

API 입력 감사 6,963개, E4B 최종 720회 토큰 일치와 현재 블록 위치 검사는 통과했다. 현재 증거에서 Phase 12 계산 결함이나 전송 중 데이터 손실을 탈락 원인으로 볼 근거는 없다. 기존 문자열 판정의 한계는 원문 검토로 분리했으며, 위 의미 오류를 단순 채점기 오류로 취소하지 않는다.

### 아직 확정하지 않은 원인

- 분류 단계에서 페르소나·상태를 제외하면서 정적 대상 설명까지 부족해졌는지, `문`과 작성 정의의 `성문/gate`를 다른 것으로 보는지가 첫 가설이다. 실제 API 대사는 어느 문인지 되묻는다. 그렇다고 모든 문을 하나의 성문으로 간주하는 보정은 정당화되지 않는다.
- 현재의 `uncertain` 지침이 실제 모호성보다 넓게 적용되는지 확인해야 한다. `uncertain`을 없애거나 모두 `match`로 바꾸면 행동 오탐을 만들 수 있다.
- 위치만 가진 배열이 칭찬·모욕의 의미 대응을 어렵게 하는지는 미확정이다. **인덱스 변환 버그는 발견되지 않았다.** 출력 형식을 바꾸는 효과는 트리거 순서 교환 실험으로 따로 검사한다.
- 최신 상태 우선 지침을 추가하는 것만으로는 다른 대상의 상태 혼동을 해결하지 못했다. 사실의 대상 표현, 지침 충돌과 과거 답변의 영향은 각각 나누어 비교해야 한다.

Structured Outputs는 형식에 맞는 응답 안의 의미 오류까지 제거하지 않는다. 따라서 schema 변경만으로 정확도 향상을 확정하지 않는다. [OpenAI 공식 안내](https://developers.openai.com/api/docs/guides/structured-outputs#handling-mistakes)

## 보완 설계

### 1. 의도 판정과 대상 확인의 경계 명확화

- 분류 지침을 현재 발화, 현재 발화가 가리키는 이력, 작성된 트리거 정의라는 세 자료로 정리한다. 권한·호감도·이전 거절과 모델의 연기 지침은 계속 제외한다.
- 작성된 트리거가 고정 게임 행동에 연결돼 있다는 사실과, 모델이 알아야 하는 자연어 대상의 범위를 구분한다. 구체 Scene 객체·실행 권한을 추론하게 하지 않는다.
- 대상 이름·동의 표현이 필요한 경우 기존 `conditionDescription`에 작성자가 명시하는 방법을 먼저 검증한다. 기존 V4 DTO에 필드나 행동 파라미터를 추가하지 않는다. 정적 대상 설명과 가변 허가 상태를 섞지 않는다.
- 명시적 현재 요청과 하나로 해석되는 참조는 정상 분류하고, 복수 대상이 끝내 남는 참조만 보류하도록 의미를 명확히 한다. 인용·회상·보고·취소는 현재 실행 요청과 구분한다.
- 문자열 포함 여부로 신호를 강제하거나 샘플의 문·호감도 ID를 제품 코드에 특례로 넣지 않는다. 트리거 설명 변경과 공통 프롬프트 변경의 효과를 별도로 기록한다. 개선이 특정 작성 데이터에만 의존하면 그 범위와 필요한 설정을 공개한다.

### 2. 복합 발화와 분류 결과의 대응 관계 보완

- 기존에 추가했던 ‘각 절을 독립 판정하라’는 문장을 다시 추가하는 것으로 끝내지 않는다. 화자·대상·현재/과거·긍정/부정·취소 범위가 다른 절을 포함한 개발 사례로 실제 차이를 확인한다.
- 분류 내부 출력의 후보로 **요청마다 부여한 짧은 키와 판정의 명시적 대응**을 시험한다. 예: 작성된 트리거를 `t0`~`t15`에 대응시키고 각 키의 값만 `match/no_match/uncertain`으로 반환한다. 키는 신뢰된 요청에서 생성하며 임의 행동 ID·인자는 생성하지 않는다.
- 누락·추가·중복 키를 거부하고 등록 순서로 원래 ID를 복원한다. 기존 배열 API를 쓰는 외부 코드가 있으면 호환 경로를 유지하고 새 내부 형식을 별도로 검증한다. V4와 `AiNpcResponse`는 그대로다.
- 같은 정의의 순서 교환과 의미 없는 ID 이름 교환에서 결과가 유지되는지 검사한다. 효과가 확인되지 않거나 16개 트리거·256 출력 tokens 한도에 문제가 있으면 형식 변경을 채택하지 않는다.
- 대사 단계에는 확정 신호와 보류된 신호의 대응을 구분해 전달한다. 하나의 전역 불확실성 값 때문에 명확한 다른 절까지 모호한 요청처럼 다루지 않도록 한다. 대사 단계가 판정을 수정하거나 행동을 추가할 권한은 없다.

### 3. 현재 사실과 대사 단계의 책임 정리

- 과거 대화, 사용자 개인 정보, 최신 관찰을 분리하는 기존 처리를 유지한다. 사실 ID·종류·작성 문장을 이용해 현재 사실의 출처와 대상을 명확히 표시하는 입력 후보를 시험한다.
- 프로토콜의 ‘대사만 생성’ 규칙이 작성된 캐릭터/lore 안의 추론 처리 지시로 바뀌지 않게 한다. 작성 데이터의 일반 행동 규칙은 대사에 반영하되 새로운 분류·게임 권한으로 해석하지 않는다.
- 자연어 fact를 코드에서 임의로 의미 분석해 새로운 사실로 만들거나, 불편한 이력·현재 데이터를 자동 삭제하지 않는다. 언급된 대상과 동일한 관찰이 없으면 그 한계를 답하고 다른 대상의 상태로 대체하지 않는다.
- 정상 요청에 대한 답변, 모호한 요청의 구체적인 되물음, 현재 상태의 직접 답변을 평가 항목으로 둔다. 발화를 그대로 복창하는 것으로 과업을 완료했다고 보지 않는다.
- 로컬은 기존 실제 행동 결과 최종화 뒤에만 기억·화면을 확정한다. Backend에는 이번에도 새 행동 결과 동기화 프로토콜을 추가하지 않으며, 생성 대사가 게임 효과 완료를 선행 주장하지 않는지 검사한다.

### 4. 유지할 실행 계약

모델 호출은 트리거가 있으면 최대 두 번, 없으면 한 번이다. 로컬 1 FIFO 슬롯·35초, Backend 30초, 단계별 256 출력 tokens를 유지한다. 실제 템플릿의 토큰 계산과 두 단계의 동일한 이력 범위를 보존한다. 입력 증가가 한도를 넘으면 기존 규칙대로 오래된 성공 이력을 양 단계에서 함께 제외하고 현재 입력 자체가 초과하면 거절한다.

분류 또는 대사 실패·생성 중 취소는 상태·행동·기억에 반영하지 않는다. 행동 단계 이후의 기존 확정 규칙, `CanExecute`, 최대 한 행동, cooldown/once, reset 분리와 NPC별 상태 수명은 변경하지 않는다. 입력·출력 원문은 고정 합성 조사 자료에만 보존하고 일반 로그에는 남기지 않는다.

## 개발 실험과 새 평가

### 단계 A — 새 자료와 비교 규칙을 먼저 고정

기존 96개와 이미 결과를 본 24개는 각각 **기존 회귀 / 관측된 추가 회귀**로 보존한다. 파일·기대값·원래 보류 평가 기록을 수정하지 않는다. 새 후보에서 이 자료를 개발에 이용한 뒤 다시 미관측 평가라고 부르지 않는다.

별도 **36개 보류 사례**를 후보 출력 확인 전에 작성·검토·해시 고정한다. 명시 요청/능력 질문, 참조/취소, 복합 태도/대상, 현재 상태, 개인 기억, 인용/모호한 요청을 각각 6개로 구성한다. 36개의 현재 문장은 중복 없이 작성하고 적어도 세 NPC 역할과 다른 대상·트리거 이름을 사용한다. 단순한 기존 문장 동의어 교환에 한정하지 않는다. 기대 신호·효과·대사 과업·상태/회상 채점 대상 여부를 미리 명시한다.

새 사례의 문장·이력·예상 답을 프롬프트 예시로 옮기지 않는다. 사람이 기대값을 검토하고 의미가 모호한 사례는 출력 확인 전에 고친다. 모델 출력을 본 뒤 기대값을 바꾸지 않는다. 자동 채점과 원문 검토를 나누는 절차는 [OpenAI 평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)에 맞추되, 사용자 데이터 수집 대신 허용된 합성 자료만 사용한다.

### 단계 B — 모델별로 원인을 분리하고 후보 하나를 선택

제품 소스가 아닌 새 검증 복제본에서 진행한다. 기존 동결 후보를 C0로 보존하고 새 후보에 별도 ID를 부여한다. 각 쌍에서는 한 가지 요소만 바꾼다.

| 개발 묶음 | 고정 anchor 수 | 비교 요인 | 시도 상한 |
| --- | ---: | --- | ---: |
| 대상·참조·불확실성 | 6 | 정적 대상 정의 또는 참조/보류 지침 중 사례별 하나 | 54 |
| 복합 절·신호 대응 | 6 | 절별 입력 표현 또는 키 기반 출력/순서 중 사례별 하나 | 54 |
| 현재 사실·대사 책임 | 4 | 사실 블록의 대상 표현 또는 단계 지침 우선순위 중 하나 | 36 |
| 합계 | 16 | 원본·한 요소 변형·원복을 각각 3회 | 144 |

개발 상한은 **단계별 실제 생성** 수다. 의도 항목은 분류만, 대사 항목은 고정된 분류 결과로 대사만 실행한다. 기대 분류 주입은 원인 분리용이고 실제 행동을 실행하거나 모델 채택 점수에 포함하지 않는다. 원본·변형·원복이 모두 변동하면 지침의 인과 효과를 확정하지 않는다. 조건이 없는 새 재시도를 덧붙이지 않는다.

각 anchor·변형·실행 순서·판정 규칙을 실행 전에 고정한다. 같은 한도를 E4B와 API에 적용하되 모델별 결과를 보고 따로 후보를 선정한다. 공통 형식과 파이프라인을 우선 사용하고, 지침 문구의 모델별 차이가 필요하면 코드에 숨기지 않고 후보 ID로 관리한다. 런타임 중 실패에 따라 다른 후보로 자동 전환하지 않는다.

**두 모델 후보를 모두 고정한 후에만 새 보류 사례의 출력을 확인한다.** 한 모델의 새 결과를 보고 다른 모델 후보를 수정하는 것도 금지한다. 후보 선택 단계에서 유효한 보완이 없으면 그 모델은 이번 작업의 미채택으로 종료한다.

### 단계 C — 회귀와 새 사례로 채택 여부 판정

- 기존 96개와 관측된 24개: 새 후보를 각 2회 실행한다. 두 집합의 점수는 별도 계산한다.
- 새 36개: 같은 입력으로 기존 SinglePass와 새 후보를 각각 2회 실행한다. 새 후보와 현재 기본 경로의 같은 시기 비교는 이 집합에서 수행한다.
- API 호출 상한을 유지하기 위해 기존 120개의 SinglePass는 이번에 다시 호출하지 않는다. 기존 결과는 역사적 참고치이며, 새 후보의 과거 집합 개선 폭을 동시 대조 실험으로 표현하지 않는다. API 별칭이 같아도 내부 모델이 같다는 가정은 하지 않는다.
- 전체 턴 결과와 중복을 제거한 분류 입력 그룹의 결과를 함께 보고한다. 반복 실행은 재현성 관찰이며 서로 다른 새 사례로 세지 않는다.
- 신호의 집합 완전 일치, 행동 오탐, 정상 요청 누락, `uncertain` 빈도, 변수 신호 오변경, 현재 상태, 개인 회상과 대사 과업 충족을 따로 집계한다. Basic/Advanced는 같은 반환 ID로 재생해 규칙 계산과 의도한 효과를 분리한다.
- 상태·회상은 단어 포함 여부만으로 채점하지 않는다. 대상·시점·소유자·정정 이력을 원문으로 확인한다. 애매한 답변을 유리하게 해석하지 않으며, 판정 보류는 통과로 계산하지 않는다.

채택 기준은 낮추지 않는다. 모든 평가 집합에서 행동 신호 오탐 0건, 신호 95% 이상, 상태·기억 90% 이상, 정상 비교 중 생성 오류·timeout 0건을 요구한다.

| 집합 | 신호 통과선 | 상태·기억 통과선 |
| --- | ---: | ---: |
| 기존 96 × 2 | 183/192 | 35/38 |
| 관측된 24 × 2 | 46/48 | 22/24 |
| 새 36 × 2 | 69/72 | 상태 6 + 회상 6을 지정하면 22/24 |

새 집합의 상태·기억 분모가 작성 검토에서 바뀌면 출력 확인 전에 `ceil(0.90 × 분모)`를 고정한다. 하위 항목 점수와 대사 과업 충족률도 공개한다. 새 집합에서 요청 복창·무관한 회피로 과업을 못 마친 턴은 대사 과업 실패로 세고 90% 이상을 요구한다. 행동 완료의 허위 선행 주장과 실제 로컬 행동 결과 최종화 불일치는 필수 환경 검사의 실패로 다룬다.

### 단계 D — 통과 모델만 제품 연결과 실제 환경 검사

의미 기준을 통과한 조합에 한해 NPC/Builder 전략 선택과 비교 샘플을 연결한다. 미통과 모델은 기존 SinglePass를 유지하고 채택 목록을 열지 않는다. 모델·실행기·입력 후보 식별정보를 함께 기록한다.

현재 소스로 Server 143개와 root·Built-in/Legacy Unity EditMode 350개 전체에 새 검사를 추가한다. 변경한 schema/파서·키 대응·16개 트리거·출력 한도, 이력 일치·토큰 경계, 단계 실패/취소·Busy·큐·늦은 완료, NPC 격리·reset·행동 1회와 Builder/Prefab/Awake의 외부 호출 0회를 확인한다. SinglePass 직렬화 입력·schema·공개 생성자와 버전 의존성은 그대로인지 검사한다.

라이선스 확인 후 수정 소스의 root·consumer·Windows x64 Mono에서 회차당 12턴을 두 번씩 진행한다. 선행 기억 생성도 12턴에 포함한다. 참조·관계 누적·허가/거절·최신 상태·두 NPC·대화/행동 reset·실행 직전 상태 변경·최종 대사·기억·종료 정리를 검증한다. 반복 Play와 Domain Reload 비활성화, API 실제 취소 후 같은 세션 복구도 확인한다.

속도 기준은 계속 **워밍업 후 전체 NPC 제출 p95 5초 이내**다. 큐·입력 준비·각 생성·검증·행동·로컬 최종화·기억/화면 반영까지 `LastSubmissionSeconds`로 측정한다. 계측 종료가 실제 반영 뒤인지 자동 검사로 확인한다. 첫 준비·워밍업, p50/p95/최대, 실패율과 느린 표본을 별도로 보존한다. 의도적으로 지연시킨 취소 경계 실험을 정상 지연 집합과 섞지 않되 일반 비교의 timeout은 숨기지 않는다. 환경별 표본 수를 공개하고 24턴만으로 일반 성능을 보장하지 않는다.

## 실제 API 호출 상한과 중단 조건

다음 구현 작업의 **새 누적 상한을 1,000회로 제안**한다. 이전 캠페인은 720회에서 종료된 상태로 보존하며 잔여분을 합산하거나 장부를 초기화하지 않는다. 이번 계획 작성의 새 모델 호출은 0회다.

| 용도 | 최대 실제 upstream 시도 |
| --- | ---: |
| 모델별 원인 분리·개발 단계 | 144 |
| 기존 120개 × 후보 2회 × 2단계 | 480 |
| 새 36개 × 2회 × (단일 1 + 후보 2) | 216 |
| 핵심 12턴 × 2회 × 3환경 × 2단계 | 144 |
| 준비·워밍업·실제 취소/복구 | 16 |
| 합계 | 1,000 |

호출 전에 durable 장부에 기록하고 실패·취소·준비도 센다. 완결된 실험 블록의 예산이 없으면 시작하지 않는다. 예산 부족이나 인증·권한·할당량·rate-limit 오류는 미수행으로 기록하고 가능한 로컬 검사는 계속한다. 실패 표본을 재시도로 교체하지 않는다. 의미 기준에 미달하면 해당 모델의 환경 호출을 진행하지 않는다.

기존 서버와 사용자 세션을 유지하고 새 격리 loopback 서버에 합성 fixture만 주입한다. 키는 사용자 환경변수로만 받으며 전달·추출·파일 저장을 요구하지 않는다. `reasoning.effort=none`, `store=false`, SDK retry 0과 기존 시간 예산을 유지한다. 검증 포트는 임시 도구의 설정이며 실제 게임에 별도 검증 서버를 요구하는 구조로 만들지 않는다.

## 변경 범위와 완료 조건

후속 구현의 우선 변경 후보는 다음과 같다. 제품 연결은 의미 기준 통과 뒤에 진행한다.

- `Runtime/Unity/Networking/LocalInferenceJsonCodec.TwoStage.cs`, `LocalInferenceJsonCodec.StageReader.cs`, `Runtime/LocalInference/LocalInferenceIntentValidation.cs`: 단계 입력·내부 결과 대응과 검증. 필요 시 새 내부 타입을 추가하되 기존 공개 호출을 보존한다.
- `server/src/two-stage-generator.ts`와 관련 테스트: 같은 분류/대사 책임·strict 검사·진단. 일반 단일 호출 생성기는 변경하지 않는다.
- 기존 Unity/Server 추론 테스트와 검증 하네스: 원본 입력 대조, 순서/이름 교환, 불확실성·실패 경계, 새 의미 판정과 호출 상한.
- 통과 후 `NpcConversationBehaviour`, Character Builder, 모델 채택 목록과 별도 비교 샘플: 기존 준비된 연결 초안을 재검토한 뒤 적용하고 실제 환경에서 검증한다.
- 결과·사용 안내·계약 안내·Unreleased: 모델별 채택과 미채택, 필요한 작성 설정과 의미적 한계를 구분한다.

새 메서드에는 기능 주석을 달고 관련 호출부를 검사한다. 에셋은 Unity API로 생성하고 기존 YAML/GUID를 직접 변경하지 않는다. Phase 12 상태·규칙 엔진, SinglePass 기본값, 이전 완료 증거와 Phase 13·14 후보는 보존한다. WSL·관리자 실행·push·태그·릴리즈는 수행하지 않는다.

한 모델만 통과하면 그 조합만 지원 상태로 기록한다. 모두 실패하면 원인별 증거와 다음 미확정 가설을 남기고 종료한다. 기준을 낮추거나 보류 사례로 재튜닝해 이번 평가를 다시 통과 처리하지 않는다. 구조 구현, 모델 의미 평가, 실제 환경 검증이 모두 통과하기 전 전체 완료로 표시하지 않는다.

검증·빌드·로그는 `E:\CodexValidation\<새 작업ID>`, TEMP/TMP·캐시는 `E:\CodexTemp\<새 작업ID>`를 사용한다. evidence에 입력/소스/설정 해시·필수 합성 원문·실행 명령·결과를, delivery에 통과한 최종 빌드·설정·재실행 안내를 보존한다. 완료 전에 이번 작업 소유의 불필요한 복제본·캐시만 절대경로·소유권·사용 여부·링크를 확인해 정리한다.
